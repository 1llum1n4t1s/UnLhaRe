# 長距離LZ候補の調査（2026-11-13）

[ゲート](GOAL_GATE_20261113.md)の2つ目の未見集合enwik8で、LHC（revision 11、PPM order 5）はサイズ0.993倍・展開12.9倍で不合格だった。原因は1MiBの独立blockで長距離の一致を使えないことと、PPMの逐次復号が遅いことである。長距離の一致を使うLZ系の候補で、どこまで届くかを7-Zipの設定違いで見積もった。測定は `D:\tmp\lhc-perf\lzscan.ts` による方向決めの1回測定で、正式比較ではない（Windows x64、7-Zip 26.05、作成 `-mx9 -mmt4`、展開は `-mmt1` と `-mmt4`、他の作業による負荷の揺れあり）。

## 分かったこと

- **長距離の一致がサイズの大半を決める**。同じLZMAで窓を1MiBから64MiBへ広げると約14%縮む。1MiB窓同士ではLHCのPPM（26.37MB）がLZMA（28.93MB）より約9%小さいが、長距離の一致を使える7-Zip d8mにほぼ並ばれる。
- **サイズ条件はLZMA級＋64MiB窓で届く**。d64mで0.935倍、d32mで0.948倍（余裕がほぼない）。d192mでもd64mから0.3%しか縮まない。
- **展開条件もLZMA級なら届く**。単一streamのLZMA復号は1スレッドで約0.8秒（約120MB/s）で、上限（約1.1秒）に収まる。自前のdecoderがこの速度の約75%以上を保てばよい。
- **作成条件が壁**。7-Zipはd64mで単一streamになり、並列化が効かず58秒かかる（基準のd8mは4スレッドで並列に分割でき24〜37秒）。高速な一致探索（hc4）はサイズを大きく失い、速くもならなかった。
- **PPMを全体で使うと最小だが遅い**。PPMd o6は0.844倍と最小だが、展開が20秒（基準の約57倍）で、復号条件と両立しない。

## 候補の設計案

1. **窓を共有したsegment並列LZ（推奨）**：入力を8〜16MiBのsegmentへ分け、各segmentは自分より前の生データ全体（最大64MiB）を辞書として参照できるようにする。符号化時は生データが全部手元にあるため、一致探索とparseはsegmentごとに並列にできる。entropy modelはsegmentごとに初期化し、復号は「segmentごとのentropy復号（並列）」と「一致のコピー（逐次、memcpy程度で高速）」の2段に分ける。7-Zipが単一streamでしか使えない大きな窓を、並列の作成・復号と両立させるのが狙い。modelの初期化による損失は1%未満と見込むが未測定。
2. **長距離重複除去の前段＋既存portfolio**：長い一致（例えば32 byte以上で1MiBより遠い）だけを前段で参照へ置き換え、残りを既存の1MiB blockで圧縮する（lrzip・srep型）。既存のblock並列を保てるが、enwik8ではPPMの復号の遅さが残るため、単独では展開条件を満たさない。
3. **費用込みの方式選択**：小〜中規模のfile群は既存のportfolio（PPMが強い）、大きいstreamは1の長距離LZ、のように書庫内で方式を選ぶ。CanterburyやCalgaryのような小さい集合では長距離LZは効かない（全fileが8MiB未満）ため、両方が要る。

いずれもblockをまたぐ参照を持つため、新しいarchive revisionと、solid streamの単位（file群をまとめる範囲）、streamの途中が壊れたときの検出と公開単位を設計し直す必要がある。

### 分かったこと

- **サイズは上限にわずかに届かない**。窓56MiBでも0.952倍で、7-Zip d64m（0.935倍）より約1.8%大きい。原因はsegmentごとのmodel初期化と、研究LZのparse・modelの差の両方で、今回の計測では切り分けていない。
- **作成が2〜4倍遅い**。各workerが前置（最大56MiB）をBTへ挿入し直すため、segmentを細かくするほど重複が増える（8MiBで106秒）。研究LZ自体も約1.3〜2.7MB/sと遅い。
- **復号も上限を超える**。逐次で約65MB/s（1.48〜1.55秒）で、7-Zip LZMAの1スレッド（約120MB/s）より遅い。entropy復号だけを並列にする2段方式は未実装。
- **見込み**：今の研究LZを土台にした「窓共有segment並列」では、サイズ・作成・復号の3条件とも届かない。届かせるには、(a) 前置をworkerごとに挿入し直さない共有の一致索引（全入力のsuffix arrayなど）、(b) LZMAより強いliteral・距離のmodel（サイズで約2%）、(c) 約1.5倍速い復号（2段並列化を含む）の3つが同時に要る。

### 2. Rustの逐次LZMA復号は速度条件を満たせるか

`examples/lzma_decode_probe.rs`（LZMAの公開仕様に沿った独自実装、safe Rust、出力全体を1つのVecに置く）で、xz 5.x の `-F lzma --lzma1=preset=9e,dict=64MiB,nice=273,mf=bt4` が作ったenwik8のstream（24,827,755B、d8m基準の0.935倍）を復号した。

| 復号器 | 時間（enwik8 100MB） | 速度 |
| --- | ---: | ---: |
| 自前のRust（5回の最小値、全byte一致） | 796.9ms | 125.5MB/s |
| 参考：xz -dc（プロセス起動・pipe込み、1回） | 720ms | — |
| 判定の上限（基準の4スレッド展開の3倍） | 約1,070〜1,220ms | 約82〜93MB/s |

## waveごとの並列segment形式の試作（2026-11-13、開発測定で判定ではない）

試作（`examples/longlz_probe.rs` の `--segment-kib` / `--wave`）に、並列に復号できるsegment形式を入れた。

- **参照の規則**：segment k（wave内の位置j）は、自分のsegment内と、waveの開始より前のデータだけを参照できる。同じwaveの前のsegment（`wave_start..seg_start`）は参照しない。一致のcopy元はどちらかの範囲に収まる必要があり、waveより前の範囲から写す一致はwave開始で切る。
- **初期化**：segmentごとにmodel・state・rep履歴・range符号器を初期化する。literal文脈の直前byteはsegment先頭では0とし、一致byte文脈は、そのbyteを読める場合だけ使う（符号化・復号で同じ規則）。
- **一致探索**：索引（BT4）は全体で1つのままで、報告する一致だけを規則で切り詰める（禁止範囲の候補は報告しない）。木の状態はデータと窓・cutだけで決まる。
- **容器**：`LLZSEG1\0`、生データ長、segment長、wave幅、窓長、segment数、各body長、body列。segment長とwave幅は形式の値で、復号のthread数から決めない。
- **復号**：waveごとに、segmentを最大4threadで並列に復号する。各segmentはwaveより前の出力と自分の出力だけを読む。
- **検証**：E.coli・book1・enwik8の各設定で、4threadと1threadの復号とも全byte一致。wave幅1で符号化した容器のwave幅を4へ書き換えると、復号器は「match source outside the segment scope」で拒否した（1thread・4threadとも）。

- 損失の主因は、同じwaveの前のsegmentを参照できないことである。segmentが長いほど参照できない直近のデータが増えて悪化し、wave幅を2にすると損失が半分以下になる。segmentごとのmodel初期化の損失は、512KiBでも小さい。
- **wave幅2・segment 1〜2MiB** が有力で、サイズは0.942倍（上限まで約0.8%の余裕）、4thread復号は約0.46秒（基準7-Zipの4スレッド展開0.36秒の約1.3倍）。wave幅4は復号が最速（約0.25秒、7-Zipより速い）だが、サイズの余裕は0.1〜0.2%しかない。
- **残る壁は作成時間**：1スレッドで約77〜84秒。一致探索（約66秒）が逐次のため、segmentを並列にparseするだけでは届かない。

### 次の段階：並列の一致探索

- 4byte hashで木を分け、各threadは全位置を走査して2/3byte hashの表を自分で更新し、自分の分担のhashの位置だけ木を組み替えて一致を出す。木の節は同じhashの節としかつながらないため、書込みは分担ごとに分かれる。
- 巡回配列はthread間で共有するため、配列長を「窓長＋許容遅れL」とし、一定の区間ごとにthreadをそろえて遅れをL以下に保つ。遅れたthreadが読む節を、先行するthreadが上書きしないようにするためである。
- wave（例：2MiB×2）ごとに「並列の探索で全位置の一致を求める」→「segmentを並列にparseする」を繰り返す。見込みは、探索66秒÷4＋parse約15秒÷2で20〜25秒程度だが、同期の費用は未測定。

## 並列の一致探索（2026-11-13、開発測定で判定ではない）

試作に `examples/longlz/par.rs`（`longlz_probe enc --threads N`）を足した。

- **分担**：4byte hashを256区分に分け、領域（約4MiB、waveの整数倍）ごとに位置数を数えて、各threadの位置数がそろうよう区分を割り当てる。各threadは領域の全位置を走査し、2/3byte hashの表は各自で更新、自分の区分の位置だけ二分木を組み替えて一致を出す。木の節は同じhashの節としかつながらないため、書込みは分担ごとに分かれる。
- **巡回配列**：thread間で共有し、長さを「窓長＋領域長」にする。threadは領域の終わりでそろうため、遅れたthreadがまだ読む節を先行するthreadが上書きすることはない。
- **parse**：領域内のsegmentを並列にparse・符号化する（segmentごとにmodelを初期化するため互いに独立）。
- **先読み**：少し先の分担位置について、hash先頭・木の最初の節・候補位置のdataを `_mm_prefetch` で先に読み込ませる（結果は変えない）。
- **一致の検証**：一致の結果はデータ・窓長・cutだけで決まるため、並列版の出力は逐次版と**byte単位で一致**する。book1、E.coli（窓1MiBで巡回あり、thread数3・4）、bible.txt、enwik8（segment 1MiB／wave 2）で一致を確かめた。

## バイナリの研究：符号長の内訳と、literal modelの見積もり（2026-11-14、開発測定で判定ではない）

### 符号長の内訳（`LLZ_STATS=1`、segment 1MiB・wave 2）

range符号器がbitごとの −log2(確率) を分類別に足した値。

| 分類 | rustlib.bin | enwik8 |
| --- | ---: | ---: |
| 一致か literal かの判定 | 7.89% | 3.43% |
| literal（一致byte文脈なし） | 23.47% | 2.63% |
| literal（一致byte文脈あり） | 25.33% | 3.07% |
| rep の選択 | 5.38% | 0.87% |
| rep の長さ | 9.22% | 0.64% |
| 一致の長さ | 6.40% | 15.11% |

rustlibは約半分（48.8%）が literal で、強くする対象は literal である。

### literal modelの見積もり（`LLZ_SHADOW=1`、出力streamは変えない）

実際の符号化はLZMAと同じliteral modelのままで、同じliteralの各bitを別のmodelで符号化した場合の −log2 を足す（parseは変えない）。予測は、0: LZMAと同じ文脈、1: 直前byte全体、2: 直前2byteのhash、3: 一致byte全体。これらを「一致byte文脈か×bit位置」の16組の重みでlogistic混合する（`LLZ_SHADOW_MASK` で予測を選ぶ）。

| 方式（rustlib、全体23,731,205Bに対して） | literalの符号長 | 全体に対する節約 |
| --- | ---: | ---: |
| LZMAのliteral（実測） | 11,578,886B | — |
| 混合：予測0のみ（数え方の違いだけ） | 11,483,323B | 0.40% |
| 混合：予測0＋1 | 11,289,494B | 1.22% |
| 混合：予測0＋3 | 10,969,387B | 2.57% |
| 混合：予測0＋1＋2 | 11,195,538B | 1.62% |
| 混合：予測0＋1＋3 | 10,835,617B | 3.13% |
| 混合：予測0〜3すべて | 10,766,765B | 3.42% |
| 混合なし：一致byte全体の単一文脈（直前byte上位3bitあり／なし） | 11,729,517／11,717,222B | −0.63／−0.58% |
| 混合なし：LZMAの確率を「一致byte全体×節」で補正（APM） | 11,413,772B | 0.70% |

- 効くのは**一致byte全体を文脈にした予測の混合**で、0＋1＋3で3.13%、すべてで3.42%。rustlibは0.979倍から約0.948〜0.946倍になり、上限0.95倍をわずかに下回る見込みだが、余裕は0.1〜0.2%しかない。見積もりは浮動小数の計数器を使っており、予測0だけでも0.40%出るため、整数の実装では小さくなりうる。
- 混合しない方式（単一文脈、補正表）はほとんど効かないか悪化する。segmentごとにmodelを初期化するため、大きな表は学習が間に合わない。
- 混合は復号でbitごとに複数の表と重みの計算が要り、wave 2の並列度では展開の上限（7-Zipの3倍、rustlibで約0.9秒）に収まるかが未確認。parseでもliteralの価格計算が重くなる。

### 作成時間：rustlibでは探索とparseの両方が7-Zipの約2倍遅い

| 設定（rustlib、4thread） | 探索 | parse | 作成 |
| --- | ---: | ---: | ---: |
| 窓64MiB（従来） | 12.4〜15.5s（thread間の偏り大） | 4.8〜6.5s | 17.3〜22.1s |
| 窓8MiB | 17.0s（偏り大） | 6.9s | 19.7〜23.9s |
| 窓64MiB＋runの内側を木へ入れない（下記） | 11.1s（各thread 9.5〜10.1s） | 6.0s | 17.3s |
| 参考：7-Zip LZMA2 d8m fb273 `-mmt4` | — | — | 8.1〜8.5s |

- **窓を8MiBにしても速くならない**。遠距離の参照が遅さの原因ではなく、作成の処理そのものが7-Zipより遅い。逐次の探索だけで23.7秒（5.2MB/s、窓8MiB）。
- 同じbyteの連続（0の詰め物など）はすべて同じ木に入り、1つのthreadが4,234万位置を受け持っていた。**runの内側の位置（直前byteと続く4byteがすべて同じ）は木へ入れず、距離1・run長の一致だけを報告する**規則を、逐次・並列の両方に入れた。threadの偏りは消え、サイズはほぼ同じ（rustlib +549B、pic +0.25%、obj2 +0.06%）で、逐次版との出力一致も保った。
- それでも作成は17.3秒で、7-Zipの約2倍。thread当たりの処理量は、探索で約3.1MB/s（7-Zipは約7MB/s以上とみられる）、parseで約5.2MB/s。両方を約2倍速くしたうえで、literalの混合による増分も吸収する必要がある。

### 見込みと残りの作業

大きなバイナリ（オブジェクト書庫）で条件を満たすには、少なくとも次の3つが同時に要る。

1. 作成を約2倍速くする（探索・parseとも）。
2. literalの混合model（整数実装）で約3%縮める。見積もり上の余裕は0.1〜0.2%。
3. 混合modelの復号を、展開の上限（7-Zipの3倍）に収める。

どれも未着手で、それぞれ1回以上の作業が要る。1と3は届かない可能性もある。リンク済みのコード（.dll）は、基準の7-Zipが自動でBCJ2を使うため、さらにBCJ2相当の変換が要る。

| 7-Zip LZMA d8m fb273 `-mmt1` | 35.1s／47.8s | 34.9s／42.9s |
| 試作 逐次encoder（窓8MiB、segment 1MiB） | 36.8s／43.3s | 36.5s／41.1s |
| 試作 一致探索だけ（逐次、窓8MiB） | 20.9s／23.2s | 20.7s／22.1s |
| 7-Zip LZMA2 d8m fb273 `-mmt4` | 10.8s | 36.4s |
| 試作 並列（窓64MiB、4thread） | 20.5s | 64.2s |

（「／」の左右は別の時期の測定。）

- 1threadでは試作の逐次encoderは7-Zipと同等の速さである。
- 7-Zipは入力を独立したblockに分けて並列化するため、4threadでもCPU時間がほとんど増えない。試作のhash分担の並列探索は、各threadが全位置を走査し、メモリ上に散らばった木を辿るため、CPU時間が約1.75倍に増える。

### 独立したstreamへ分ける（7-Zip型）の見積もり

入力を4つに分け、各部分を逐次encoderで同時に符号化した（4プロセス、`llz-split.ts`）。

| 入力・設定 | 壁時計 | サイズ | d8m基準比 |
| --- | ---: | ---: | ---: |
| rustlib、4stream、窓64MiB | 20.2s | 23,997,164B | 0.990 |
| rustlib、4stream、窓8MiB | 12.6s | 24,753,707B | **1.021** |
| enwik8、4stream、窓64MiB | 21.8s | 26,526,564B | 0.999 |

- 窓64MiBのまま4つ同時に動かすと、各プロセスが約2倍遅くなる（大きな木のメモリ競合）。窓8MiBなら7-Zipに近い時間になるが、サイズは7-Zipより大きい（segmentの参照規則とstreamの分割で約2%失う）。

### 結論

大きなバイナリ（オブジェクト書庫）では、作成の速さとサイズの両立が見えない。

- 窓64MiB・hash分担の並列：サイズ0.979倍、作成は7-Zipの約2倍。
- 7-Zip型の独立stream・窓8MiB：作成はほぼ同等だが、サイズは1.02倍。

どちらからも、literalの混合model（見積もりで−3%、parseと復号がさらに重くなる）を足して両方の条件を満たす道筋は立たない。テキスト系の大きなfileで得た結果（3条件とも満たす）を活かし、判定の対象をテキスト系と小〜中規模の集合に絞るのが現実的な代案である。

## 重複の多い大きなテキストで作成が遅い原因の調査（2026-11-14、未見集合の不合格後の診断で、判定には使わない）

[ゲート](GOAL_GATE_20261113.md)の3つ目の未見集合で、作成が `sources.200MB`（7-Zipの1.49倍）と `dblp.xml.200MB`（1.96倍）で届かなかったため、原因を調べた（試作 `longlz_probe`、同じ設定・4thread・各1回の測定）。

### 探索とparseの手間

| | dblp.xml.200MB | sources.200MB |
| --- | ---: | ---: |
| 一致探索（壁時計） | 23.9s | 19.6s |
| parse（壁時計） | 12.9s | 10.3s |
| 辿った木の節 | 13.5／byte | 11.1／byte |
| 比較で進んだbyte | 114.1B／byte | 73.6B／byte |
| parseの先読み節点 | 1.00／byte | 0.91／byte |
| 一致の長さを試した回数 | 21.3／byte | 10.5／byte |

- どの位置もparseの先読みに入る（長い一致の内側を飛ばせない）。dblpのparseは1回の探索で約3,200位置（先読みの上限4,096位置の近く）を進み、nice長（273）に達する一致が連続しないため、7-Zipも同じ作りで同様に全位置を調べる。
- 一致探索は、4スレッドでほぼ均等（各22.5s）に分担できている。分担の偏りが原因ではない。

### 設定を変えた効果（dblp、4thread）

| 設定 | サイズ | 探索 | parse | 作成合計 |
| --- | ---: | ---: | ---: | ---: |
| 既定（cut 152・nice 273） | 21,950,775B | 23.4s | 13.3s | 36.8s |
| cut 64 | 21,957,894B | 23.0s | 12.8s | 35.8s |
| cut 32 | 22,035,333B | 22.3s | 12.8s | 35.2s |
| nice 128・cut 64 | 21,982,432B | 22.7s | 9.7s | 32.4s |
| nice 64・cut 32 | 23,203,121B | 22.8s | 6.4s | 29.3s |

- 探索の深さ（cut）を変えても探索は約22〜23秒のまま動かない。位置ごとの固定の費用（索引の読込み待ち）が主で、木の深さではない。
- nice 128・cut 64はparseが約27%短くなり、作成が約12%短くなる（サイズ+0.14%）。それでも7-Zip（19.8s）の約1.6倍。nice 64はサイズが+5.7%で採れない。

### 7-Zip型の独立stream（4分割）の見積もり（各部分を逐次encoderで4プロセス同時に符号化）

| | 壁時計 | サイズの合計 | d8m基準比 |
| --- | ---: | ---: | ---: |
| dblp（窓は各50MB） | 29.7s | 23,090,196B | **0.965** |
| sources | 28.0s | 32,536,969B | **0.976** |

- どちらも7-Zip（dblp 19.8s、sources 20.3s）より遅く、サイズも0.95倍に届かない。4プロセスが各64MiB級の木を同時に動かすとmemoryの取り合いになり、1プロセス当たりの速度が落ちる。独立streamへの分割は、この条件では解にならない。

### 結論

- 1threadの逐次encoderは7-Zipとほぼ同じ速さ（rustlibで36.8s対35.1s、窓8MiB）だが、窓64MiBの探索は、7-Zipの窓8MiBよりmemory待ちが重い。重複の多いデータでは7-Zipは速くなる一方、LHCは位置ごとの固定の費用が変わらない。
- 調整（cut・nice）で縮められるのは約12%まで。作成を7-Zip以下にするには、位置ごとのmemory読込みを大きく減らす構造の変更（例：木の節とその位置の先頭byteを同じ領域に置く、窓を32MiBへ縮める、近距離と遠距離で索引を分ける）が要り、いずれも複数回の作業で、届く保証もない。
