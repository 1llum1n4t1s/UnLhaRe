# 未見集合 unseen4（2026-11-15、本人が固定）

[ゲート](GOAL_GATE_20261113.md)の大きなテキスト系fileの判定に使う未見集合。開発集合の6つ（enwik8、`sources.200MB`、`dblp.xml.200MB`、`english.200MB`、`linux-6.6.tar.200MiB`、`simplewiki-pages-articles.xml.200MiB`）がrevision 15（`long-range-mix-trial`）で開発目標を満たした後、2026-11-15に本人が「固定して取得」を選んだ。測定の前に下のSHA-256を記録し、以後は結果を見て入れ替えない。

## 判定の手順

- 候補：製品の Release CLI、`lhc-create --strategy long-range-mix-trial --threads 4 --no-fsync`（`eb73939` のsource）。
- 比較：7-Zip 26.05 `a -t7z -mx9 -m0=LZMA2:d8m:fb273 -mmt4`、展開は `x -mmt4`。
- 入力ごとに、ウォームアップ1回の後、LHC→7-Zip／7-Zip→LHCを交互にした9往復。作成・展開とも、プロセス起動・書込み・CRC検査を含む壁時計の中央値で比べ、毎回の展開結果を元のfileとbyte比較する。
- 合格：サイズが7-Zipの0.95倍以下、作成が2.0倍以内（8MiB以上の単一file）、展開が3.0倍以内、全回のbyte一致。Windows x64 で測り、macOS ARM64 の最終確認は別に行う。

## 不合格2つの原因と改善（2026-11-15〜16）

### 診断（llz-diag ビルド、各5回の中央値、ゲートの手順ではない）

- 固定費ではない：1KiBの入力の展開は LHC 10ms／7-Zip 14ms。
- literal の混合が展開を1.8〜2.6倍にしていた。
  - bgl：混合あり（全25 wave）690ms、混合なし381ms。混合なしではサイズが0.9552で不合格。
  - proteins：混合あり5,189ms、混合なし1,993ms（サイズ0.837）。
- 4 threads の伸びが1threadの1.7〜1.8倍しかない。同時に復号できるのは wave の2 segment だけで（`WAVE = 2`）、wave の境目で main が受け取り・4MiBの複製・CRC・書込みを終えるまで次の wave を投入しなかった。

### 改善A：展開の待ちを次の wave と重ねる（`src/lhc/pipeline.rs`、形式・出力は不変）

- 受け取った block を複製せず `Segment`（`Arc<Vec<u8>>`）として履歴へ足し、すぐ次の frame を投入する。次の wave が履歴待ちなら、wave の残りの block も先に受け取ってから投入し、CRC と書込みは後で書庫順にまとめて行う。
- 旧CLIと新CLIの展開の対の比較（10往復、他のセッションの負荷あり）：中央値で bgl 936→801ms、linux 1,165→1,080ms（10往復すべて新が速い）、english 1,402→1,289ms。

### 改善B：literal が多い wave は混合しない（`src/lhc/longlz/mod.rs` の `choose_mix`）

11集合（開発6つと unseen4 の5つ）の wave の記録（混合を選んだ wave）：

| 集合 | 混合した wave | 節約 bit / literal | literal / 生データ byte |
| --- | ---: | --- | --- |
| bgl | 25 / 25 | 0.112〜0.175 | 0.036〜0.074 |
| dblp | 17 / 25 | 0.164〜0.327 | 0.015〜0.040 |
| english | 4 / 25 | 0.165〜0.281 | 0.000〜0.032 |
| enwik8 | 3 / 12 | 0.229〜0.293 | 0.029〜0.052 |
| jawiki | 15 / 25 | 0.190〜0.319 | 0.023〜0.052 |
| linux | 23 / 25 | 0.116〜0.310 | 0.013〜0.052 |
| llvm | 16 / 25 | 0.097〜0.457 | 0.001〜0.056 |
| proteins | 25 / 25 | 0.073〜0.088 | 0.096〜0.755（0.096 の1つ以外は0.23以上） |
| sese | 3 / 25 | 0.251〜0.319 | 0.020〜0.034 |
| simplewiki | 13 / 25 | 0.115〜0.227 | 0.031〜0.058 |
| sources | 13 / 25 | 0.126〜0.259 | 0.018〜0.034 |

- 節約 bit / literal は proteins（最大0.088）と llvm（最小0.097）の間に隙間がほとんどないので採らない。
- literal の密度は proteins 以外が0.074以下、proteins が（1 wave を除き）0.23以上で、上限 1/8（0.125）はその間に3倍近い余裕を持って入る。「混合する bit の数を生データの byte 数以下にする」と読める。
- 無圧縮になる frame の literal は数えない。
- 新旧CLIの書庫の比較：proteins 以外の10集合は byte 一致、proteins だけ 59,923,998 → 60,871,011B。

### 改善A・Bの後の正式手順の判定（2026-11-16、bgl と proteins だけ）

| 名前 | サイズ比 | 作成比 | 展開比 | 判定 |
| --- | ---: | ---: | ---: | --- |
| bgl | 0.9341（7,911,789 / 8,470,357） | 1.752（47,217 / 26,956） | 2.833（689 / 243） | 合否線上で未確定（開発目標は未達） |
| proteins | 0.8368（60,871,011 / 72,742,717） | 0.927（50,450 / 54,446） | 1.910（2,135 / 1,118） | 合格 |

- 測定中も他のセッションの負荷があった。7-Zip の展開は bgl で222〜300ms（前回の中央値228ms）、proteins で837〜3,255ms と揺れ、proteins の比は7-Zip側の揺れで小さめに出ている（負荷の少ない診断では混合なしで2.5倍前後）。
- bgl は未解決。比が3.060から2.833に下がった主因は7-Zip側が228→243msに遅くなったことで、LHCの中央値は699→689ms（1.4%）しか動いていない。前回の7-Zipの中央値で割ると689 / 228 = 3.02、最小値どうしでも635 / 222 = 2.86で、開発目標2.8に届かない。
- 改善Aが正式手順でほとんど効かなかった理由を、一時的なプロセス内の計時（測定後に外した）で確かめた。4 threads、5回、他の負荷あり：

  | 集合 | 全体 | main の受け取り待ち | CRC＋書込み | worker の復号時間の合計 |
  | --- | ---: | ---: | ---: | ---: |
  | bgl | 747〜914ms | 680〜839ms | 59〜66ms | 1,326〜1,651ms |
  | linux | 966〜1,136ms | 891〜1,054ms | 59〜83ms | 1,736〜2,042ms |

  - CRC＋書込みは200MiBあたり約60msで、architect の推定（直列区間約130ms）より小さい。改善Aで重ねられる分はもともと小さかった。
  - worker の復号時間の合計は全体の約1.8倍で、同時に2 segment という形式の上限（2.0倍）にほぼ達している。bgl の展開時間は「segment の復号時間 × 50 ÷ 2」でほぼ決まる。
  - bgl を開発目標2.8倍（約640ms）に入れるには、segment の復号を約1割速くするか、同時に復号できる単位を増やす（形式を変える案 C：segment 内の command と literal を別の range 符号に分けて2 thread で追う）必要がある。
  - literal の密度の上限を下げて bgl の一部の wave だけ混合する案は、linux・jawiki・llvm・simplewiki・enwik8 の wave（密度0.052〜0.058）も反転させ、linux のサイズの余裕（0.0008）を崩すおそれがあるので採らない。
- 全回で展開結果は元のfileとbyte一致した。
