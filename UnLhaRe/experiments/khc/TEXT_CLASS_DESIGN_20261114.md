# 大きなテキスト系の改善設計（revision 12 の次、2026-11-14）

[ゲート](GOAL_GATE_20261113.md)の4つ目の未見集合で、Linuxカーネルのソースtar（`linux-6.6.tar.200MiB`）のサイズが7-Zipの0.971倍となり不合格だった。本人の「テキスト統合を設計」の指示を受け、サイズを詰める設計をまとめる。実装には入らない。この文書は、形式を変える設計として、実装前に architect（設計分析担当）へ渡す依頼の下書きを兼ねる。

## 3. 設計案

効果が大きく、見積もりの根拠がある順に、段階的に進める。各段階は、次の段階へ進む前に開発集合6つで効果と3つの予算（後述）を確かめる。

### 段階1：LLZのsegmentを4〜8MiBへ（約1.0%）

- LHCのblock（1MiB）とLLZ segmentを分離する。LLZ segment＝連続するS個のblock（S＝4〜8）で、segment内のblockは同じmodelと状態を引き継ぐ。wave 2（2 segmentを1組）は変えず、各segmentはwave開始より前の同じentryだけを参照する。
- LLZ1BLKのframeはblockごとのままにし、headerのflagで「segment内で前のblockからmodel・rep・range coderを引き継ぐ」を表す。range coderは1blockごとに終端する（frame単位の検査・一覧・事前走査を保つため）。
- 展開は1 segment（4〜8blockを逐次）が1 job。並列度は2のまま。`pipeline.rs`は、jobがblock列と履歴を持ち、wave前のsegmentの消費後に次のwaveを投入する（今のblock単位の仕組みの粒度を変える）。
- 作成：parseはsegment内でmodelを引き継ぐため逐次になる。200MiBなら25〜50個のsegmentがあり4threadで並列にできるが、8〜32MiBのentryではsegmentが1〜8個で並列度が下がる（小さなentryは時間が短く許容）。
- **memory**：`par.rs`の領域は1 segment×wave以上になり、一致置き場の最悪値がsegment長に比例して増える（4MiB領域の4倍＝16MiB領域で約2倍の最大使用量。許可した約1.2GiBを超えうる）。一致の持ち方を詰める（1つ8Bを5〜6Bへ、1位置の最大数を16から8へ）か、領域をsegmentから切り離す（parseが要る範囲の一致だけを持つ）。実際の最大使用量を測って報告する。

### 段階2：distanceとlengthのmodel強化の見積もり（最大の見込み）

- 符号長の85%が距離と長さで、literalの8%より桁違いに大きい。まず、literalで使った「影のmodel」と同じ方法で、**出力を変えずに見積もる**。見積もる候補：
  1. distance slotの文脈を、直前の一致のslot・長さの状態・位置（entry内のoffset）で増やす。
  2. 長距離の一致の直接bit（30.4%）のうち、上位の数bitを文脈つきにする。
  3. 直前の距離に近い距離（rep0との差が小さい）を表す記号。
  4. 長さのmodelを、直前の長さ・距離のslotの文脈で増やす。
- 各案の節約の見積もりが、全体の1.5%以上あれば次へ進む。1%未満なら、この方向は採らない。

### 段階3：literalの混合model（約1.0%、見積もり）

- 段階2の後に判断する。見積もりを整数（12bit確率、表引きのstretch/squash）で作り直し、実際の節約と、literal数当たりの復号時間（literal数をstatsへ追加）を測る。展開は2-way並列のままで、englishが2.47倍（上限3.0）のため、混合modelは展開時間の増加を約15%以内に収める。parseのliteral価格の計算も重くなる点（作成の予算）に注意する。
- 見積もりが整数で0.7%を下回るなら採らない。

### 段階4：天井の判断（本人）

- 段階1〜3を合わせても、Linux tarが0.95倍に届かない場合：tarのようなソースの集合は、7-Zipの窓を広げた上限（0.947）が条件の直前にあり、LZMA級の方式では届かない種類として、判定の対象から外す（または条件を緩める）判断を本人に求める。届く見込みの目安は、構造（約1.0%）と他の改善の合計が、約2.1%以上（0.971→0.95）になるか。

## 7. 段階2の見積もり結果（2026-11-14、出力を変えない測定）

試作（`examples/longlz/shadow2.rs`、`LLZ_SHADOW2=1`）に、一致の記号列を強いmodelで符号化し直した場合の符号長だけを足し合わせる「影のmodel」を入れて測った。parseと出力は変えない。入力は開発集合の5つ（segment 1MiB・wave 2の製品設定）。counterはf32で楽観側になりうるが、基準（現在と同じ文脈）の見積もりは実際の符号長と近い（Linuxのslotは見積もり39.60Mbit・実測39.63Mbit、長さは37.80Mbit・実測37.21Mbit）ため、差は信頼できる。

| 案（全体に対する節約、%） | linux | simplewiki | english | sources | dblp |
| --- | ---: | ---: | ---: | ---: | ---: |
| 長さを「slot・直前の長さ・state・pos」の混合（slotを先に送る）。混合入力4つ | 0.90 | 0.84 | 1.01 | 0.81 | 1.59 |
| 同、入力3つ（pos×slot区分、直前の長さ、state） | 0.70 | - | 0.90 | - | 1.37 |
| 同、入力2つ（pos×slot区分、直前の長さ） | 0.58 | - | 0.89 | - | 1.18 |
| slot（長さの文脈なし・混合） | 0.04 | 0.04 | 0.02 | 0.03 | 0.48 |
| 直接bit上位6bitの混合 | 0.39 | 0.17 | 0.29 | 0.40 | 0.33 |
| align 4bitの混合 | 0.12 | 0.11 | 0.14 | 0.14 | 0.12 |
| 近傍距離（rep距離との差が±4096以内なら差で符号化） | **0.95** | 0.35 | 0.06 | **1.09** | 0.58 |
| 合計（長さは入力4つ） | **2.40** | 1.51 | 1.52 | 2.47 | 3.10 |

- 近傍距離は、4つのrep距離の最も近いものとの差を、適応する木と符号1bitで送る案。使われる割合は一致の7%前後で、符号の選択は1bitのflag（適応）。範囲を±4096から±1M（20bit）に広げても変わらない（12bitで十分）。
- 512byte境界（tarのfile先頭）を指す距離の特別扱いは、Linuxで0.03%しか効かない（採らない）。
- slotの文脈（直前のslot・長さ）は、dblpを除いて効かない。長さの文脈にslotを使う（slotを先に送る順にする）ほうが効く。
- 長さの文脈の混合なしの単一文脈は、Linux・dblpで長さの約1〜3%（全体の0.2〜0.6%）しか効かず、englishだけ約6%（0.79%）。効果の大半は混合による。直接bit上位の単一文脈はLinuxでは平坦より悪い（混合が必要）。
- 合計は5つとも1.5%以上で、設計の判定基準（1.5%以上）を満たす。ただし**混合は復号時間を増やす**（下記）ので、全部を採る前提にはならない。

### 復号時間の見立て（未測定、実装前の見積もり）

- Linux 200MiBの一致は約8.1M個。長さ・slot・直接bit・alignの混合対象bitは1つの一致で約20bitなので、全部を混合すると約160Mbitの混合になる。整数の3入力混合を1bit当たり6〜8nsとすると約1〜1.3秒のCPU時間で、今の復号のCPU時間（約1.4秒＝wall 0.73秒×並列度約2）に対して**+70〜90%**になる。englishの余裕（2.47/3.0）を超える。
- 費用対効果の高い順は、近傍距離（混合なし。1つの一致に1flag、復号の増加は数%）、長さの混合入力2〜3つ（約5.6bit/一致、+15〜25%）、直接bit上位・alignの混合（bit数が多く効果が小さいので後回し）。
- 並列度を増やせば復号の壁時間は縮められる。block 1MiB・wave 2に対して、大きなsegmentならwave 4のサイズ損失が小さくなる可能性がある。段階1の測定で確かめる（1MiB・wave 4は0.988で損失が大きかったが、segmentを大きくすれば変わりうる）。

### 判定

- 見込みは大きいが、近傍距離（0.06〜1.09%）と長さの混合（0.6〜1.6%）の2つを優先する。形式を変えない測定で「0.95倍に届く見込みがある」ことは確かめられた：Linuxの現在0.971に、segment（約1.0%）、近傍距離（0.95%）、長さの混合（0.6〜0.9%）、literalの混合（約1.0%、浮動小数の見積もり）を足すと、見積もりの上では約0.93〜0.94になる。整数実装と復号時間の制約で、実際は見積もりの7割程度に減ると見て、約0.945。余裕は小さい。
- 次の実装順は、(1) 近傍距離（混合なし、parseの価格に近傍を入れる）、(2) segment 4〜8MiB、(3) 長さの混合（入力2〜3つ）。各段で開発集合6つの測定を行い、復号が2.8倍を超えるなら混合を減らす。

## 8. 近傍距離の実装結果（2026-11-14）

見積もり（章7）の通り、近傍距離（直近のrep距離との差が65536以内の距離を、基準番号・符号・差で書く）を試作→製品（archive revision 13、LLZ1BLK frame revision 2）の順に実装した。

- **符号**：通常一致の先頭に近傍flag（文脈は更新前state）。flag=1なら長さの後に、基準の番号（2bit木、文脈 min(長さ-2,3)）、符号（i別）、差-1（i別の5bit slot木＋直接bit）。正規形（同じ距離のrepが先にある番号は不可、rep距離と等しい距離はrep記号で書く）はdecoderが拒否する。詳細は`LHC_FORMAT.md`のrevision 13。
- **サイズ**（revision 12比）：linux 1.275%、sources 1.471%、dblp 0.832%、simplewiki 0.547%、english 0.014%。見積もり（linuxで約0.95%）より大きく、全入力で悪化なし。
- **時間**：展開は同等（english 7-Zip比2.35）。作成はparseの距離価格が増え、`dist_costs`で長さ範囲に当たる文脈だけを計算するようにして約+2.5%（dblp 7-Zip比1.85）に収めた。
- **検証**：製品のframe payloadが試作のsegment bodyとlinux 200/200、dblp 200/200 blockで一致。悪性記号列（別名の選択、rep等値、下溢れ、窓外、wave内の他block）と版の取り違えの拒否を単体・e2eで確認。`build.ps1 -Test`通過。
- **残り**：linuxの7-Zip比は約0.958見込み（revision 12は0.971）。次の候補はsegment 4〜8MiB（約1.0%）、長さの混合（0.6〜0.9%、復号時間の増加に注意）、literal混合（約1.0%、float見積もり）。7-Zip d64mの0.947が目安の上限。

## 9. segment 4MiB（revision 14、2026-11-14）

- **見積もり**：試作でsegment 1→4MiB（近傍あり）はlinux −1.0%、english −2.7%、dblp −0.5%、sources −0.2%、simplewiki +0.16%。12〜32MiBの先頭ではsimplewikiが+0.7〜1.1%、englishは−7〜−19%。
- **作成時間**：単純に4MiBにするとparseの並列度が半分（領域8MiBに2 segment）になり+25〜40%。領域を広げると一致置き場の最悪値が約2.9GiBになるため、探索の同期単位（1MiB）とparseの単位を分け、置き場640MiBの上限で完成済みsegmentを先にparseする方式にした。本人が作成時memoryを2GiBまで許可。
- **結果**（製品、交互測定）：5入力すべてが7-Zipの0.95倍以下（linux 0.949、sources 0.930、dblp 0.906、simplewiki 0.919、english 0.886）。展開は7-Zipの2.03〜2.57倍でrevision 13と同等。作成はrevision 13と同等だが、dblpは7-Zip比1.94〜2.04で2.0の上限際（開発目標1.9は未達）。
- **残り**：開発目標（サイズ0.945、作成1.9）にはlinuxのサイズとdblpの作成が届いていない。次の候補は長さの混合（0.6〜0.9%、復号時間増）とparseの高速化。

## 10. 作成の高速化（出力不変、2026-11-15）

- **内訳**（dblp、revision 14、4thread、変更前）：find は壁時計27.7秒・CPU約117秒、parse は壁時計約17秒・CPU約62秒。find の約48%は64MiB窓の二分木を辿る memory 待ち、約5%は4 thread が全位置で2/3byte hash を重ねて更新する分。parse は `tail_rep0` 約6%、`dist_costs` 約6.5%、長さの繰り返し約10%。
- **変更**：探索単位の前処理（2/3byte hash の更新と区分の振り分け）を1 thread にまとめ、次の単位の前処理を今の単位の探索と重ねた。`advance` の巡回位置を除算なしで求め、`common` を SSE2 の16byte比較にし、`dist_costs` と `tail_rep0` の結果を覚えた。revision 12/13 の探索単位も1MiBにした（出力は不変）。見積もりは前処理32MiB分増え、`LONG_RANGE_CREATE_MEMORY_BYTES` 1160MiB、`LONG_RANGE_WIDE_CREATE_MEMORY_BYTES` 1448MiB。
- **確認**：revision 12/13/14 × thread 1/4 の書庫が変更前とbyte一致（dblp 200MB、linux・dblp・englishの先頭）。7-Zipとの交互測定で dblp 39.7〜40.5秒（7-Zip比1.54〜1.59、変更前1.78〜1.85）、linux 33.8〜34.6秒（比1.21〜1.23）。peak は4threadで1.34〜1.47GiB。
- **残り案（未実装）**：find と parse の重ね合わせ（出力は不変だが約8 thread・索引+128MiBが要り、`--threads` の意味が変わる。dblp約26〜27秒の見込み）、nice 128・cut 64（出力が変わる。parse −27%、サイズ+0.14%）。
